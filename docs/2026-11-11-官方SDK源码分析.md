# 官方 SDK 源码分析：PHY 侧坏读值的三条修复思路

> 初版：2026-11-11 20:55（GMT+8）
> 起因：72 h 守夜确认 `0007` 只拦住 carrier 翻转，`speed` 瞬态
> （-1 / 10 / 1000，2–3 s 恢复）仍在，说明 PHY 侧坏读值没被消除。
> 方法：拉取 GL.iNet 官方同型号 SDK `gl-inet/gl-rtl8366ub` @ `b214b53`
> （内部代号 RTL8371C，134 文件 + 1.36 MB 寄存器字段表），与本驱动逐函数对照。

> **2026-11-11 22:50 后续更新**：本文 1.3 节提出的「锁域可交错」假设，
> 已由当天的实机 A/B 实验**证实**——统一锁开 150 s / 18,328 次 OCP 读 **0 坏读**，
> 锁关 150 s / 18,878 次 **7 次坏读**，且 `speed=-1` 瞬态同步出现。
> 结论与数据见 [P0 根因定位报告](2026-11-11-P0根因定位报告.md)。
> 因此下文「仍在测试中」的第 1 项已升级为已验证，思路 1 即为落地实现。

## 0. 先更正三个已被源码排除的假设

| 假设 | 核查结果 | 判定 |
| --- | --- | --- |
| `reg_read()` 发 READ_OP 后不等完成、缺完成确认 | 三家（本驱动 / 官方 SDK `smi.c` / RTL8372N 外部驱动）逐行一致 | **排除** |
| OCP 事务缺互斥，并发读会串扰 | 本驱动 `rtl8366ub_ocp_read()` **已有** `mutex_lock(&priv->phy_mutex)` 包住 prepare→CMD→wait→RDATA 全过程 | **排除** |
| 芯片硬件去抖 `LINK_DOWN_CHK @ 0x01B8` 没配是根因 | 全仓 grep：SDK 只有字段定义（`regField_list.c:8427`、`reg_list.c:4557`），**没有任何写入**；`SMI_CTRL @ 0x27A4` 的 `SMI_POLL_MASK` 同理 | **下调**（厂商量产同样不配，只能当可选实验，不能当根因） |

## 1. 源码已论证

### 1.1 官方 SDK 的链路状态有两条完全不同的通道

| 通道 | 函数 | 寄存器 | 用途 |
| --- | --- | --- | --- |
| **PHY OCP** | `dal_rtl8371c_port_phyStatus_get()`（`dal_rtl8371c_port.c:1327`） | OCP `0xA434` BIT(2) + bits 10/9/5/4/3 | 量产 swconfig 的 `sw_get_port_link()`（`rtl8366ub_mdio.c:446`）用户态查询；中断里打日志（`mdio.c:921`）。**不翻内核 carrier** |
| **MAC 侧状态** | `dal_rtl8371c_port_macStatus_get()`（`dal_rtl8371c_port.c:1758`） | `MAC_STATUS @ 0x284C`，每端口 16 bit 数组 | 官方 DSA 的 `phylink_mac_link_state()`（`rtl8366ub_dsa.c:393-402`）：`state->link = status.link` |

`MAC_STATUS` 字段（`rtk_rtl8371c_regField_list.c:9948-10040`）：
`LINK_ABLTY` **bit 6**、`DUPLEX_ABLTY` bit 4、`SPEED_ABLTY` **bits 3:0**
（编码 0=10M、1=100M、2=1000M、3=500M、5=2500M，见
`dal_rtl8371c_port.c:34-38`）、TX/RXPAUSE bit 8/7、`NWAY` bit 9。
另有 `PHY_STATUS @ 0x285C` 同布局。

**关键差异**：官方给 phylink/carrier 的是 **MAC 侧锁存状态**，走一次普通
`reg16_array_read`；本驱动的 `rtl8366ub_phy_read_status()` 把 **PHY 内部 OCP
resolved 位**直接赋给 `phydev->link`。这就是「把状态喂给谁」的具体落点。

> 官方那份 `rtl8366ub_dsa.c` 是**未编译的死代码**（`src/Makefile` 无
> `rtl8366ub_dsa.o`，量产走 swconfig），所以本节只能证明「SDK 里有这个设计
> 意图」，**不能**证明「量产验证过 MAC_STATUS 更可靠」。

### 1.2 官方 SDK 对 `0xA434` 的解码比本驱动严格

`phyStatus_get()` 在 `link=1` 时只认 **6 种合法位组合**
（2500M / 1000M / 100M×2 / 10M×2），全部不匹配直接
`return RT_ERR_FAILED`（`dal_rtl8371c_port.c:1380-1381`），调用方不更新任何状态。

本驱动 `rtl8366ub_phy_read_status()`：

- 100M / 10M 分支少检查 `BIT(3)`；
- 非法组合落到 `else phydev->speed = SPEED_UNKNOWN`（**就是守夜日志里的 `speed=-1`**）；
- 而且无论解码是否合法，前面已经 `phydev->link = link`。

所以守夜观测到的 `-1` 有确定来源；`10` / `1000` 是**合法但明显错**的组合，
说明坏的不是某一位，而是整个 16 位读值。

### 1.3 最根本的一条：SDK 用一把全局锁，本驱动用四把互不相干的锁

SDK（`rtk_switch.h:46-48`、`rtk_switch.c:35`）：

```c
DEFINE_MUTEX(rtksw_api_mutex);
#define RTKSW_API_LOCK(unit)   mutex_lock(&rtksw_api_mutex)
```

全仓 **26 个 .c、543 处** `RTKSW_API_LOCK`，每个对外 API（含
`rtksw_port_phyStatus_get`，`port.c:218-220`）都把整个调用串行化。也就是说
`prepare → CMD → poll BUSY → 读 RDATA` 以及其他任何寄存器序列，在 SDK 里
**不可能互相插入**。

本驱动的四把独立 mutex（`rtl8366ub_dsa.h:51-54`）：

| 锁 | 覆盖范围 |
| --- | --- |
| `reg_mutex` | DSA 操作（`dsa.c`） |
| `phy_mutex` | 仅 `ocp_read` / `ocp_write`（`port.c:91,116`） |
| `table_mutex` | L2 表操作 |
| `mib_mutex` | MIB 统计（`mib.c:58-81`） |

而 `rtl8366ub_reg_read()/reg_write()` 底层只持 `bus->mdio_lock`，保护的是
**单次** MDIO 事务（写 `CTRL0=31` → `ADDRESS=23` → `CTRL1=21` → 读/写 `DATA=25`）。
所有间接访问都靠这组**全局共享**寄存器来「选地址」。

于是存在真实的可交错窗口：

```
线程 A (phylib, phy_mutex):  ocp_prepare 写 OCP_MSB / INDACC_ADDR ──┐
线程 B (LuCI 读统计, mib_mutex): 写 MIB_ADDR / 读 MIB_CMD / 读 MIB_DATA  ← 插入，改写 CTRL0/ADDR/CTRL1
线程 A:  ocp_wait → 读 INDACC_RDATA  ────────────────────────────────┘  ← 读到被覆盖的地址上下文
```

`mib.c`、`l2.c`、`cpu.c`、`dsa.c` 的寄存器序列都**不持 `phy_mutex`**，只持各自
的锁，因此都能与 OCP 事务交错。SDK 的单全局锁不存在这个问题。

这一条能同时解释所有观测事实（解释力 ≠ 已证实，**2026-11-11 已由 A/B 实验证实**）：

- 坏值是整个 16 位字、且有时落在合法组合 → 像读错地址/读错端口的数据，
  而非 PHY 真实重协商；
- `carrier` 恒 1 但 `speed` 乱跳 → `0007` 只过滤了 carrier 翻转，没消除坏读本身；
- 7 次瞬态**全部**落在有 LuCI 登录 / SSH 会话的活跃时段，而 44 h 无人操作时
  零瞬态 → LuCI 概览页轮询 `get_stats64`（`mib.c`）是天然的并发读者；
  守夜脚本只读 sysfs carrier/speed，不触发 MIB；
- 原厂单次采样没问题 → 全局锁保证事务完整。

## 2. 三条可落地的修复思路（按贴近根因排序）

### 思路 1（首选，SDK 全局锁语义）：统一 MDIO 间接访问的互斥域 — **已验证**

把 `reg_read/reg_write` 提升为「持一把 `indirect_lock` 的公共入口」，让
mib / l2 / cpu / dsa / ocp **所有**序列串行化；`ocp_read/ocp_write` 内部改用
不持锁的 `__reg_read/__reg_write`（否则自锁）。等价于 SDK 的 `RTKSW_API_LOCK`。

- 改动文件：`rtl8366ub_reg.c`、`rtl8366ub_port.c`（都在 `795-10` 本体 / `0001`）。
- 风险：低（纯加锁），但要逐一检查嵌套调用，确认没有持 `indirect_lock` 时
  再调公共 `reg_*`。
- 这是唯一能**修所有 OCP 消费者**（`phy_read`、`init.c` patch 序列、
  `get_stats64`）的方案，也最符合主线驱动的正确性要求。
- **实测结果**：锁开 150 s / 18,328 次读 / 0 坏读；锁关 150 s / 18,878 次读 /
  7 坏读。见 [P0 根因定位报告](2026-11-11-P0根因定位报告.md)。

### 思路 2（架构对齐）：carrier / speed 改读 `MAC_STATUS @ 0x284C`

扩展已有的 `rtl8366ub_port_get_mac_pause()`（已在读 `0x284C + physical_port*2`），
同时解析 `LINK_ABLTY` bit6、`SPEED_ABLTY` bits3:0、`DUPLEX` bit4，替代
`ocp_read(0xA434)` 作为 `phydev` 状态源。

- 与 SDK `phylink_mac_link_state()` 的设计意图一致；改动量小。
- 局限：仍走同一个 `reg_read`，思路 1 的并发缺口会影响它，只是不再影响 PHY
  OCP 通道；且官方 DSA 是死代码，没有量产背书。
- 需要实机验证真实拔插的响应延迟（MAC 侧锁存可能比 PHY 侧慢）。

### 思路 3（保守补充）：按 SDK 严格校验 `0xA434` 位组合

只认 6 种合法组合，非法则判定本次读取无效、直接 `return 0` 保持上次
`phydev->*`（可选先重读一次）。这样 `speed=-1` 会消失，`0007` 的状态机有机会
整体删除。

- 局限：`speed=10` / `1000` 是合法组合，单靠校验拦不住。只能作为 1/2 之后的
  防御层，不能单独当根因修复。

> 无论选哪条，最终目标都是**删掉 `0007` 的 workaround**：坏读在源头被消除，
> 而不是靠「连续 2 个轮询周期」过滤后果。

### 后续可做的最小观测实验（零风险，只加观测）

照 RTL8372N 外部驱动的 `phy_ocp` 思路做一个 debugfs，一次读取并打印：

```
0xA434 (OCP RDATA 原始 16 位)
0x284C (对应端口 MAC_STATUS 原始 16 位)
0x1f02 (INDACC_STATUS)
+ 在 mib 读序列首尾打原子计数，标记本次 OCP 是否与 MIB 交错
```

等下一次 `speed` 瞬态出现时对比：

| 观测 | 判定 |
| --- | --- |
| `0xA434` 异常、`0x284C` 恒 2500M、且伴随 MIB 交错 | 思路 1 成立，加锁后可直接删 `0007` |
| `0xA434` 异常、`0x284C` 也异常 | 是 MAC/PHY 真实瞬态，方向要改（查芯片状态机 / 硬件去抖） |
| `0xA434` 合法但错（10/1000）、`0x284C` 恒 2500M | 支持「读错地址上下文」交错假设，同时说明思路 3 单独不够 |

## 4. 与「进主线」的关系

问题全部位于 **`0001`（`795-10` 本体）**，即 GL.iNet 提交、仍 open 的
PR #24237 四提交之一。两种推进方式：

- **更贴主线**：把本文 1.3 的锁域分析 + 实测数据整理成 PR #24237 的 review
  comment / issue，让上游在 `795-10` 本体里修；本地不叠补丁。
- **本地先验证**：用「补丁套补丁」新增 `0008` / `pending-6.18/795-13`，保持
  `0001`–`0004` 字节不变；验证有效后再决定是回推上游还是保留增量。
  （2026-11-11 已按此路径验证成功。）

改 `0001` 本体需先征得维护者同意。本仓库当前只保留 `0001`–`0007`，
统一锁补丁尚未入库。
