# P0 根因定位报告：MDIO 间接访问序列未串行化

> 日期：2026-11-11 21:10 – 22:50（GMT+8）
> 设备：GL-MT5000，ImmortalWrt `master` @ `4765b65762` / Linux 6.18.60
> 性质：本地测试固件实机验证记录。相关固件**未发布**，仅用于本地刷机测试。
> 本文严格区分「已验证」与「仍在测试中」，未实测项不作结论。

---

## 0. 结论先行

**P0「PHY 侧坏读值」的根因已定位并验证修复**：官方 SDK 用一把全局锁
（`RTKSW_API_LOCK`）串行化所有 MDIO 间接访问，而本驱动有四把互不相干的
mutex，普通寄存器访问序列可以插入 OCP 事务中间、改写共享的地址/控制寄存器，
导致读到错误数据。加上事务级串行化后，实测**坏读从 7 次 / 150 s 降到 0 次 / 150 s**，
`speed` 瞬态同步消失。这是**根因修复**，`0007` 的软件去抖因此具备删除条件。

本轮同时抓到两个真实代码缺陷（probe-defer 导致 debugfs 绑定悬空 `priv`、
`0006` 的 `port_change_mtu` 缺失），并补齐了此前积压的大部分测试项。

## 2. 已验证

### 2.1 编译与产物

- v1 / v2 两次均 `BUILD_EXIT=0`；每次 `sha256sum -c` **16 项全 OK**；
  manifest **180 包**（正式口径 172 + 5 个调试包 + 依赖）。
- 调试包全部落地：`tcpdump / iperf3 / ethtool / ip-full / strace`；
  内核 `CONFIG_DEBUG_FS=y`、`CONFIG_DYNAMIC_DEBUG=y`；
  `NET_DSA_REALTEK_RTL8366UB=y`、`NET_DSA_TAG_RTL8366UB_8021Q=y`。
- 预置网络脚本确认已打包进 `root-mediatek/etc/uci-defaults/`。

### 2.2 刷机与自举（不保留配置）

`sysupgrade -n` 后，仅靠固件预置即自动恢复：

| 项 | 结果 |
| --- | --- |
| LAN | `192.168.1.1/24` |
| root 凭据 | 可用，SSH 正常登录 |
| WAN | `proto=pppoe`、`up=true`，重启后自动拨号 |
| 四口 | lan1 / lan2 / eth0 / eth1 全部 `carrier=1 / 2500M / up` |
| 预置脚本 | 已执行并自动删除（幂等：只填缺失项，不覆盖已有配置） |

即 `-k`（保留配置）与 `-n`（干净配置）两条路径都验证过：`-k` 在 v1 通过，
`-n` 在 v2 通过。`-n` 更干净，且真正检验了预置脚本，后续循环建议继续使用。

### 2.3 P0 根因：锁域 A/B（决定性证据）

debugfs 观测口在 v2 修复后数值正常（`serial_mdio=1`、`ocp_reads` 正常递增、
`bad_resolved=0`）。用同一固件、同一并发压力（循环读 MIB 统计并读 `regs`
触发 OCP），只切换 `serial_mdio`：

| 阶段 | 时长 | OCP 读次数 | `bad_resolved` 增量 | 异常原始记录 |
| --- | --- | --- | --- | --- |
| **统一锁开** `=1` | 150 s | 18,328 | **0** | 0 |
| **统一锁关** `=0` | 150 s | 18,878 | **7** | 7 条 |

- `overlap`（普通寄存器读与 OCP 事务重叠计数）在锁开阶段从 19 涨到 401，
  说明并发到达真实存在，只是被锁串行化而未造成破坏。
- **旁证**：守夜日志在 `22:43:22`（LOCK_OFF 阶段末尾）记录到 `lan2 speed=-1`、
  2 秒后恢复；LOCK_ON 全程无瞬态。关锁 → 坏读 + speed 瞬态，开锁 → 两者皆无。
- `regs` 正常值参考：`port 0 a434=0x3bde mac284c=0x07d5 link=1
  mac_speed_code=5 valid=1`（`speed_code 5` = 2500M，bit6 = link）。
- 坏读判据：`0xA434` 的位组合不属于 6 种合法组合之一（全 0 会被当作合法的
  link down），说明读到的是**错数据**而非单纯全 0。

结论：**「MDIO 间接访问序列未串行化」就是根因**；官方 SDK 的单全局锁正是为此
存在。`0007` 的重读 + 去抖只是过滤后果，具备删除条件（仍需长窗口确认）。

### 2.5 过程中修掉的三个坑

1. **`feeds update` TLS 截断**（`GnuTLS recv error (-9)` / `early EOF`）：
   代理软件本身正常，根因是 `git` 没有显式代理配置、大对象走 TUN 透明代理被
   截断。给 `http.https://github.com.proxy` 指定 HTTP CONNECT 代理、调大
   `http.postBuffer`、放开低速中断后恢复。
2. **刷机判定误报**：`nohup` 在 busybox ash 不存在（导致一次 sysupgrade
   完全没执行）；只探测 SSH 端口可达会在设备尚未重启时误判恢复。改为无
   `nohup` 后台执行 + 必须观察到 `uptime` 回落才算重启，并支持空密码兜底登录。
3. **probe-defer 悬空指针**：见 §3 缺陷 1，已修并验证。

## 3. 发现的代码缺陷与修复清单

### 缺陷 1（已修，v2 验证通过）

`rtl8366ub_debugfs_init()` 原在 `dsa_register_switch()` 之前调用。首次 probe
返回 `-EPROBE_DEFER` 时创建的 debugfs 目录绑定了即将释放的 `priv`；第二次
成功 probe 因目录已存在而创建失败，观测口一直指向悬空内存
（表现为 `serial_mdio=0`、`bad_resolved` 异常大负数）。

修复：移到注册成功之后。

### 缺陷 2（已定位，待修）

**`0006` 的 `port_max_mtu` 不完整**：声明 `port_max_mtu=9000`，但没有实现
`ops->port_change_mtu`，`ip link set lan1 mtu 2000` 返回
`RTNETLINK answers: Not supported`，用户口 MTU 永远锁在 1500，大包 100% 丢包。

- 另有客观上限：conduit `eth0` 的 `max_mtu` 为 **2030**
  （`MTK_MAX_RX_LENGTH_2K 2048 − 18`），DSA 会 clamp
  `min(conduit->max_mtu, max_mtu + tag_overhead)`，所以本平台**到不了 9000**；
  README 早期写的「MTU 9000 实际收发」测试目标本身需要更正为「≤2030 的 jumbo 帧」。
- `0006` 的提交说明已承认「只解除上限、硬件 MAC 仍默认标准帧长」，但连
  接口都改不动，属**声明与能力不一致**，主线 reviewer 会挑。
- 官方 SDK 存在 `MAX_LENGTH` / `MAX_LEN` / `FC_JUMBO_*` 字段，芯片可配。
  修法：实现 `.port_change_mtu` 并写最大帧长寄存器；若不想引入新功能，
  则应撤掉 `0006`，避免虚假声明。

### 缺陷 3（测试观测口小 bug，不影响主结论）

`records` 环形缓冲读取起点写成 `dbg_rec_next % MAX`（下一个待写槽），应为
`(dbg_rec_next - n) % MAX`，因此 7 条异常记录显示的是未初始化空槽（全 0），
原始坏值没抓到。`bad_resolved` 计数与 A/B 对比不受影响，下一轮一并修。

### 下一步

1. 修 `records` 读取顺序；
2. 决定 `0006` 是补全 `port_change_mtu` 还是撤掉；
3. **删除 `0007` 去抖**（根因已修），用长窗口（24–72 h）确认无 carrier 翻转
   与 speed 瞬态；
4. 把「统一间接访问串行化」整理成可提交 PR #24237 的独立补丁，附本轮 A/B 数据。
